# canteen_real_v3 审核（2026-11-15）

## 一句话

这批文件**不是食堂照片**，而是超市商品包装的正面照（400 px 缩略图），
151 个文件里只有 62 张不同照片，89 个是逐字节复制的副本，7 张图还被同时塞进
4/5/9/11/14/17/17 个不同类别。**不能用来评估单菜准确率**。

## 1. 文件层面

| 检查项 | 结果 |
|---|---|
| 文件数 | 151 |
| 不同照片数（sha256） | **62** |
| 逐字节重复的副本 | **89** |
| 一张图挂多个类别 | 7 张（最多 17 个类别） |
| 图像尺寸 | 全部短边 < 400 px（300x400 占 50 张） |
| EXIF | 无（相机信息被剥掉） |
| 与 train/val/test/canteen_clean/canteen_real 的近重复 | 0 / 62（没有泄漏） |

举例：`chocolate_cake/IMG_chocolate_cake_0001.jpg`、`pizza/IMG_pizza_0009.jpg`、
`mixed/IMG_mixed_0001.jpg`、`lasagna/IMG_lasagna_0004.jpg` 等 22 个文件是同一条字节流。

## 2. 内容层面

62 张全是**商品包装正面照**：矿泉水瓶、Perly 酸奶、Maître Coq 鸡翅袋、McCain 薯条袋、
Sodebo 冷冻披萨盒、Nutella 罐、Häagen-Dazs 冰淇淋桶、Haribo、Kinder……

也就是说：既不是食堂场景，也不是"盘子里的一道菜"，而是"包装食品照"——正是
`src/foodcls/packaging.py` 想拦、但只在照片已被判 out-of-scope 时才去改文案的那一类。

## 3. 用接口跑一遍（62 张，tables/v3_api.json）

| 结果 | 数量 |
|---|---|
| 判 in_scope（会把包装照当菜） | **36 / 62** |
| 门控判 not_food（正确拒绝） | 12 / 62 |
| 被 robust 规则拒 | 14 / 62 |
| packaging 启发式命中 | **0 / 62** |

被接受的那 36 张里，p_food 中位数 0.94，例子：`pizza/IMG_pizza_0003.jpg` 报 pizza 98 %、
`ice_cream/IMG_ice_cream_0002.jpg` 报 ice_cream 87 %——商品图上印的披萨照片确实像披萨，
模型没说错，是"包装照不该给结论文案"这件事没有生效。

**这暴露了一个真实缺陷**：packaging 检测是纯 numpy 启发式（长直边缘 + 低纹理密度），
且只在 out-of-scope 时用来改文案，所以对"印着大披萨的冷冻披萨盒"完全无感（0/62）。

## 4. 建议

1. **v3 需要真的拍**（按 data/splits/README_拍摄要求_v3.md 的清单，手机原图 2–5 MB/张，
   短边 ≥ 1000 px，有 EXIF，一个类一个文件夹，同一张图不要出现在两个文件夹里）。
2. 这 62 张不要丢——它们正好是"包装食品照"这个类别的高质量难负样本。
   可以把 packaging 从启发式换成和食物门控同一套做法的线性头（512 维池化特征，
   62 张包装 vs 食物照片），代价和门控一样（几十行、一次前向、512 个权重），
   然后把"包装照"的判定接到 in_scope 之前，就不再出现"给冷冻披萨盒报 98 % pizza"。
   需要 62 张再补 30–50 张不同品类（饮料罐、零食袋、外卖盒、保鲜膜托盘）会更稳。
3. 如果这批是你用脚本批量生成的（文件名 `IMG_<类名>_000N.jpg` 的规律很像），
   告诉我生成方式，我可以直接改脚本让它按类去重、并且不去复制同一张图。
